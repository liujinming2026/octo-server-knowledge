## 域 0：项目总览

### octo-server 是什么，解决什么问题

`octo-server` 是 **OCTO 平台的 Go 语言后端服务**，定位为"whole-platform anchor"——所有客户端（Web、Android、iOS）、管理控制台、以及 AI Agent 适配器均以此服务为唯一接入点。

核心价值：

| 能力 | 说明 |
|------|------|
| REST + WebSocket API | 供 octo-web / octo-admin / 移动端消费 |
| Lobster（AI Agent）编排 | 首类路由 / 会话 / tool-call 执行，Agent 作为对话参与者 |
| WuKongIM 控制面 | 通过薄控制面边界驱动 WuKongIM 实时消息核心，IM 核心可替换 |
| 可插拔存储 | MySQL 兼容 SQL 迁移 + 多对象存储适配器（MinIO / OSS / COS / S3 / Qiniu / SeaweedFS）|

来源: `README.md#L1-L40`

### 核心架构

```
客户端 (Web/Android/iOS/Admin)
        ↓  REST + WebSocket
   octo-server  ──────────────── WuKongIM (IM 核心，实时消息)
        │
        ├── modules/         业务逻辑模块（每模块独立 SQL + API + Service）
        ├── internal/        通用子系统（cardactiondispatch, msgextraseq, …）
        ├── pkg/             共享库（redis, botevent, pushcache, cardtmpl, …）
        │
        ├── octo-matter      Task / Todo 微服务
        └── octo-smart-summary  LLM 会话摘要服务
```

**关键组件：**

- **REST + WebSocket**：`gin`-based HTTP 框架（`pkg/wkhttp`），WebSocket 支持实时消息推送
- **WuKongIM**：实时 IM 核心，octo-server 作为 WuKongIM 的控制面客户端驱动频道/消息/在线状态
- **Lobster**：OpenClaw 驱动的 AI "数字分身"，路由与会话调度内嵌于 server，非外挂
- **modules/ 架构**：每个功能域（user/group/bot/file/oidc 等）独立为一个 module，通过 `register.AddModule` 在 `init()` 中自注册路由 + SQL 迁移文件

来源: `README.md#L50-L110`、`internal/modules.go#L1-L75`

### 8.1 数据库迁移机制

**迁移工具**：`github.com/rubenv/sql-migrate`（`go.mod#L行` 可查）

**迁移文件规范**：

- 命名格式：`YYYYMMDDNNNNNN_<模块>_<描述>.sql`（如 `20260728000001_card_template_catalog.sql`）
- 每个模块的 SQL 文件放在 `modules/<module>/sql/` 目录
- 每个 `1module.go` 通过 `//go:embed sql` 将 SQL 文件嵌入二进制

**迁移注册流程（以 base 模块为例）**：

```go
// modules/base/1module.go

//go:embed sql
var sqlFS embed.FS

func init() {
    register.AddModule(func(ctx interface{}) register.Module {
        return register.Module{
            SetupAPI: func() register.APIRouter { ... },
            SQLDir:   register.NewSQLFS(sqlFS),   // ← 嵌入 SQL 文件系统
        }
    })
}
```

来源: `modules/base/1module.go#L1-L20`

**迁移执行顺序**：按 SQL 文件名时间戳全局排序，与模块 blank-import 顺序无关。跨模块依赖（如 botfather ALTER robot 表）由时间戳保证。

来源: `internal/modules.go#L1-L25`（注释块）

**SQL 文件格式**（sql-migrate 标准）：

```sql
-- +migrate Up
CREATE TABLE event ( ... );

-- +migrate Down
DROP TABLE IF EXISTS event;
```

来源: `modules/base/sql/20191106000001_event_legacy01.sql#L1-L16`

### 8.3 对象存储

**支持的后端（6 种）**：

| 后端 | 实现文件 | 配置字段 |
|------|----------|----------|
| MinIO（自建 / 私有桶）| `modules/file/service_minio.go` | `cfg.FileService = "minio"` |
| 阿里云 OSS | `modules/file/service_oss.go` | `cfg.FileService = "oss"` |
| 腾讯云 COS | `modules/file/service_cos.go` | `cfg.FileService = config.FileServiceTencentCOS` |
| AWS S3（SigV4）| `modules/file/service_s3.go` | `cfg.FileService = "awsS3"` |
| 七牛云 | `modules/file/service_qiniu.go` | `cfg.FileService = "qiniu"` |
| SeaweedFS | `modules/file/service_seaweedfs.go` | ⚠️ 待确认配置值 |

**接口定义**：`IService` / `IUploadService` 定义在 `modules/file/service.go`，关键方法：

```go
type IService interface {
    UploadFile(filePath, contentType, contentDisposition string, copy func(io.Writer) error) (map[string]interface{}, error)
    DownloadURL(path, filename string) (string, error)
    GetFile(path string) (io.ReadCloser, string, error)
    PresignedPutURL(objectKey, contentType, contentDisposition string, fileSize int64, expiry time.Duration) (uploadURL, downloadURL string, err error)
    // ...
}
```

来源: `modules/file/service.go#L1-L60`

**预签名上传流程**（`GET /v1/file/upload/presigned`）：

1. 客户端请求 presigned PUT URL（带 `type` + `filename` + `fileSize` 参数）
2. Server 调用 `PresignedPutURL` 签名 Content-Type / Content-Length / Content-Disposition（MinIO/COS/S3 SigV4 签名强制 Content-Length；OSS V1 签名不覆盖 Content-Length）
3. 客户端直接 PUT 到对象存储（绕过 server）
4. ⚠️ OSS V1 签名下 Content-Length 仅建议性，不强制 MaxFileSize；需强制大小上限应迁移到 SigV4 后端（MinIO/COS）

来源: `modules/file/api.go#L783-L845`

**贴纸限制**：贴纸必须走 multipart `/v1/file/upload`，禁止走 presigned 路径（StickerMaxFileSize 1MB 只在 multipart 路径强制）。

来源: `modules/file/api.go#L852-L860`

**文件类型路由**（`modules/file/api.go#L1004-L1033`）：不同文件类型（头像、聊天文件、贴纸等）映射到对应 object key 前缀；存储选择在 `cfg.FileService` 统一切换。

### 9.1 go build 用法

**最快上手（本地二进制）**：

```bash
git clone https://github.com/Mininglamp-OSS/octo-server.git
cd octo-server
go build -o octo-server .
./octo-server --config ./configs/tsdd.yaml
```

来源: `README.md#L55-L60`

**私有预览阶段（依赖 octo-lib 未公开时）**：

```bash
# 1. 克隆兄弟仓库到同级目录
git clone git@github.com:Mininglamp-OSS/octo-lib.git
git clone git@github.com:Mininglamp-OSS/octo-server.git

# 2. 在 go.mod 中添加 replace 指令
replace github.com/Mininglamp-OSS/octo-lib => ../octo-lib

# 3. 拉依赖后构建
go mod tidy && go build ./...
```

来源: `BUILDING.md#L1-L35`

**Docker 构建（单镜像，标准 OSS Dockerfile）**：

```bash
make build   # 等价于: docker build -t octo-server .
```

来源: `Makefile#L1-L2`

**Dockerfile 中的 ldflags 版本注入**：

```bash
CGO_ENABLED=0 GOOS=linux go build \
  -ldflags="-w -extldflags '-static' \
    -X main.Commit=$GIT_COMMIT \
    -X main.CommitDate=$GIT_COMMIT_DATE \
    -X main.Version=$GIT_VERSION \
    -X main.TreeState=$GIT_TREE_STATE" \
  -installsuffix cgo -o app .
```

`GIT_VERSION` 回退为 `dev`（`git describe --tags --abbrev=0 2>/dev/null || echo dev`），OSS 首次 build 无 tag 时构建不中断。

来源: `Dockerfile#L24-L36`

### 9.2 Dockerfile vs Dockerfile.ghcr 的区别

#### `Dockerfile`（GitHub 发布 / OSS 用）

| 特性 | 值 |
|------|-----|
| 构建镜像 | `golang:1.25`（`FROM golang:1.25 AS build`）|
| 运行镜像 | `alpine:3.21`（`FROM alpine:3.21 AS prod`）|
| 编译方式 | 容器内 `go build`（源码构建），CGO_ENABLED=0 静态链接 |
| 版本注入 | ldflags 从 git history 读取（`git describe --tags`，无 tag 时 fallback to `dev`）|
| 用途 | 官方 Docker Hub 发布镜像（GitHub Actions 触发 `v*` tag push 自动构建）|
| GOPROXY | `https://goproxy.cn,direct`（加速国内构建）|

来源: `Dockerfile#L1-L48`

#### `Dockerfile.ghcr`（私有部署 / CI 预编译用）

| 特性 | 值 |
|------|-----|
| 构建镜像 | 无（直接接收预编译二进制）|
| 运行镜像 | `debian:bookworm-slim` |
| 编译方式 | **不含 go build**，COPY 预编译好的 `linux_${TARGETARCH}` 二进制到容器 |
| 用途 | CI/CD 管道：先在 CI 多平台交叉编译（`linux_amd64` / `linux_arm64`），再构建运行镜像 |
| TZ | `Asia/Shanghai`（同 `Dockerfile`）|

来源: `Dockerfile.ghcr#L1-L16`

**核心差异一句话总结**：`Dockerfile` 在容器内完整编译（更自包含，适合用户自己构建）；`Dockerfile.ghcr` 消费预编译好的多架构二进制（CI 流水线用，构建更快）。

### 9.3 与 octo-deployment 的关系

**octo-deployment** 是全栈一键部署仓库（`Mininglamp-OSS/octo-deployment`），包含：
- Docker Compose 全栈（octo-server + octo-admin + octo-web + octo-matter + octo-smart-summary + WuKongIM + MySQL + Redis + **MinIO** + nginx）
- Helm charts 等部署清单

**原本在 octo-server 仓库内的 `docker/octo/` 和 `docker/tsdd/` compose 已退休**，全部迁移到 octo-deployment 作为唯一权威来源。

`Makefile` 中的 `push` / `deploy` / `deploy-v2` targets 是**过时遗留**（硬编码了私有阿里云注册表路径，且 `make push` 存在 tag/push 目标不一致 bug），不应使用。

来源: `BUILDING.md#L40-L62`、`Makefile#L3-L20`

### 9.4 发布流程（SemVer + release-drafter）

1. **选定 main 分支上的 commit**，确认 CI 绿灯，记录 Actions run ID
2. **打 tag**（`git tag -a v1.7.0 -m "..." <sha> && git push origin v1.7.0`）
3. **运行 Release Publish workflow**（Actions 页面手动触发 `.github/workflows/release-publish.yml`），传入 tag + run ID；工作流重验证 CI 状态后推广 GitHub Release
4. **Docker Hub 多架构镜像自动发布**（`mininglamposs/octo-server`），由 `.github/workflows/docker-publish.yml` 在 `v*` tag push 时触发（linux/amd64 + linux/arm64）

来源: `RELEASING.md#L1-L52`

**Changelog 全自动**：PR 采用 squash merge + Conventional Commits 标题，release-drafter 自动汇聚草稿，不需手写。

来源: `RELEASING.md#L20-L35`
